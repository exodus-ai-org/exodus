# Security hardening

What protects Exodus today, what was fixed in the 2026-09-19 audit, and what is
still open. Read this before changing the HTTP server's middleware, the preload
bridge, window creation, or the artifact sandbox.

## Threat model

Exodus is local-first, but three things make it a target anyway:

1. **The API returns the saved provider keys and can run shell commands**
   (`GET /api/v1/settings`; `POST /api/v1/chat` with the `terminal` tool), and
   `exodus-ios` has to reach it over the LAN. It used to do so on a plaintext
   port open to every interface, with no authentication.
2. **The renderer shows untrusted content**: model output (markdown links,
   generated artifact code) that a web page can steer through prompt injection
   via `webFetch` / `webSearch`, plus embedded third-party frames (CodeSandbox,
   TradingView, diagrams.net).
3. **The main process is fully privileged** (file tools, `terminal`, Computer
   Use), so anything that reaches the API or IPC inherits the user's account.

## Open

### Smaller items

- `img-src *` in every CSP is the exfiltration channel for #1; narrowing it
  breaks remote images in chat unless they are proxied through main. For the
  main window this is now mitigated at the component, not the CSP: a chat
  image only auto-loads from `data:`, the media route or a search-result host
  (see "Remote images in chat" above), so an arbitrary host needs a tap first.
  The artifact sandbox's own CSP is separately `img-src * data: blob:` —
  wide open — and only `connect-src 'self'` is tight there; an `<img>` tag is
  not a `fetch`/`XHR`, so model-written artifact code can still exfiltrate
  through an image `src` without the user's page ever calling out. Not
  covered by this change (artifacts are out of `Markdown`'s render path
  entirely) and not yet fixed.
- MCP `args` masking is a heuristic over argument shapes (secret-named
  flags and `NAME=value`, secret headers, URLs, `-p` after `-u`): a secret
  inside a JSON-valued argument (`--config '{"apiKey":…}'`) or under a flag
  with an unremarkable name is returned as is (it is still encrypted at rest).
- `POST /api/v1/s3/presigned-url` hands out presigned upload URLs: their `X-Amz-Credential`
  carries `s3.accessKeyId` (a registry field; the secret key is not
  revealed), and any loopback caller gets a 15-minute upload capability to
  the user's bucket.
- A web page can embed `<img src="http://localhost:60223/api/v1/media/…">`:
  a no-cors image request carries no `Origin`, so the origin gate lets it
  through (the packaged renderer's own `<img>` is a cross-site request from
  `file://`, so `Sec-Fetch-Site` / CORP cannot tell them apart). It can
  display the image but not read its pixels, and it has to know two random
  uuids (the chat's and the file's) to name one.
- The image-download guard deliberately allows 198.18.0.0/15 (a TUN proxy's
  "fake-ip" range — every name resolves into it under Clash / Surge /
  sing-box) and Teredo 2001::/32 (poisoned resolvers answer `2001::1` for
  real hosts). Under fake-ip the proxy, not Exodus, resolves the real host:
  a proxy rule that sends an attacker's name DIRECT could still reach a
  private address. `web_fetch`'s direct fetch (`loadDocumentBuiltin`, the
  fallback after the Jina reader) does not use the guard yet — a URL the model was steered to can reach
  loopback / the LAN; moving them onto `fetchPublicHttps()` needs a
  plain-http decision first (web pages, unlike image links, are often http).
- `terminal`, `writeFile` and `editFile` run without per-call confirmation;
  the tool toggle in the composer is the only gate.
- Memory poisoning by indirect prompt injection: a page the model reads
  (`web_fetch`, a search result) can steer an autonomous `update_memory`, and
  that change persists into every later chat's `<user_memory>` block. The
  mitigation is the visible memory-change strip at the run's foot, with Undo;
  there is no confirmation before the write.
- The single-instance lock is keyed on Electron's `userData`, so it covers dev
  vs packaged Exodus but not universal-client, which shares `~/.exodus` from a
  `userData` of its own.
- Signing / notarization is not wired (`osxSign`), so ASAR integrity is only as
  strong as the unsigned bundle.
- `GET /api/v1/tools/ping-ollama?url=` fetches any URL from main (reachability
  oracle for internal hosts).
- `googleCloud.googleApiKey` is still served in plaintext by
  `GET /api/v1/settings` (`API_PLAINTEXT_EXCEPTIONS`): the map-itinerary card
  uses it in the renderer (Maps JS, Places photo URLs). It needs another way
  into Exodus's own windows (IPC) before it can be masked.
- Secrets at rest are as strong as the OS key store. On macOS the key is the
  login Keychain item "Exodus Safe Storage", whose access list admits the
  build that created it; another binary — a dev build, or an ad-hoc-signed
  update with a new `cdhash` — gets a Keychain prompt, and "Deny" makes every
  secret read as needing re-entry (the same holds for `lock.dat` and the LAN
  key). With no backend (Linux without a keyring) they stay plaintext. Chats
  are not encrypted and stay readable to a local process through the loopback
  API, `POST /api/v1/analytics/query` included.
- A value that no longer decrypts (a settings key, an MCP secret, url or
  args) is kept as stored by every save that does not move its destination —
  posted back as a mask, unset, or as the `[]` / `null` the API showed — and
  its MCP server stays unconnected until the value is typed again.
  `needsReentry` lists them.
- Changing the signing identity (the first Developer ID build) makes every
  stored secret undecryptable: the user re-enters each key once (see
  CLAUDE.md, "When a Developer ID exists").
- Backups taken before the upgrade (`~/.exodus/backups`, up to seven) hold
  every key in plaintext, and they do not age out on their own: old backups
  are pruned only when a new one is written, and the daily backup runs only
  while the app is open at 03:00 with auto-backup on — so a user who rarely
  has it open then, or has auto-backup off, keeps them indefinitely.
  `removeBackupsOlderThan()` (`backup.ts`) can delete them after the first
  post-migration backup, but it is not called: deleting backups is the
  owner's decision. The purge does not reach blocks the filesystem freed.
- Keys pasted into a chat or remembered by memory are not registry secrets:
  they stay plaintext in `message` / `memory`, in LCM's `lcm_summary` and in
  `session_summary`, in `index-message` job payloads (a full message row),
  in the Chat Audit snapshot and in Elasticsearch when it is on.
- An MCP server whose url, args or a secret does not decrypt is not
  connected until it is entered again; the raw log scrub at the one-time
  purge only knows the secrets Exodus holds now (not keys rotated since).
